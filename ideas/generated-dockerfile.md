# Shepherd writes the Dockerfile; the project declares a build

**Status:** idea, not decided. Nothing implemented. On graduation this file is deleted — if accepted, as
a `D_` entry in `DECISIONS.md` (plus whatever `R_`/matrix rows in `COMPARISON.md` it moves); if rejected,
as a one-line why-not wherever the trap would otherwise be retried.

**Raised:** 2026-09-09, out of the build-input survey in `COMPARISON.md`.

## The problem it answers

An in-repo `Dockerfile` is untrusted input that **names its own build cache**. BuildKit's `id` defaults
to the mount `target`, and the app is free to set `id=` to anything — so today the hosted project, not
Shepherd, decides which cache it shares with whom. `mvn install` of somebody else's `1.0-SNAPSHOT` is
the accident; a deliberately poisoned artifact placed in the cache another project reads is the attack.
`D_no_shared_cache` already records this as a *Known gap*: the layer cache is isolated per project by
flags on the build command, the dependency cache mount that `install` recommends is not.

The realisation behind this idea: **whoever writes the Dockerfile names the caches.** So enforcing
`R_cache_isolation` for the dependency cache means Shepherd has to be the one writing it.

## The sketch

The project stops shipping a `Dockerfile` and declares a build instead — a base image, a build command,
an artifact glob, a start command, and the directories to cache. `shepherd-build` renders a Dockerfile
from that, in a temp dir outside the repo checkout, and builds it. The repo becomes source only.

A per-project record (shepherd-java already keeps one; its schema lives there), roughly:

```json
{
  "build": {
    "baseImage": "eclipse-temurin:25-jdk",
    "runtimeImage": "eclipse-temurin:25-jre",
    "command": "./mvnw -B -DskipTests package",
    "artifact": "target/*.jar",
    "cacheDirs": ["/root/.m2"]
  }
}
```

and the file it would render, where every load-bearing decision is Shepherd's:

```dockerfile
# generated by shepherd-build for PROJECTID — not present in the repo, never edited by hand
FROM eclipse-temurin:25-jdk AS build
WORKDIR /src
COPY . .
RUN --mount=type=cache,id=PROJECTID-/root/.m2,sharing=locked,target=/root/.m2 \
    ./mvnw -B -DskipTests package

FROM eclipse-temurin:25-jre
WORKDIR /app
COPY --from=build /src/target/*.jar /app/app.jar
EXPOSE 8080
CMD ["java", "-XX:MaxRAMPercentage=75", "-jar", "/app/app.jar"]
```

The `id=` prefix is the whole point: the app never learns the cache's name, so it cannot address another
project's. `sharing=locked` is belt-and-braces on top of serial builds (`concurrentJenkinsBuilders: 1`).

## How everyone else declares a build

Every product in `COMPARISON.md` that does *not* trust a repo Dockerfile has converged on the same
shape — **commands plus named cache directories, rendered by the platform** — and two of them namespace
the cache exactly as sketched above. Read on 2026-09-09.

### Nixpacks (Railway; the default in Coolify and Dokploy) — `nixpacks.toml`

```toml
[phases.install]
cmds = ['npm install']
cacheDirectories = ['node_modules']

[phases.build]
cmds = ['npm run build']
cacheDirectories = ['node_modules/.cache']

[start]
cmd = 'npm start'
```

Phases carry `cmds`, `cacheDirectories`, `nixPkgs`, `aptPkgs`, `dependsOn`, `onlyIncludeFiles`, `paths`.
**Nixpacks renders a Dockerfile** from the plan — `nixpacks build ./app --out DIR` writes it instead of
building, `nixpacks plan ./app` prints the plan as JSON/TOML, and `--plan plan.json` replays one.

The part worth copying is `src/nixpacks/builder/docker/utils.rs`:

```rust
format!("--mount=type=cache,id={sanitized_key},target={sanitized_dir}")
// sanitized_key = sanitize_cache_key(&format!("{cache_key}-{sanitized_dir}"))
```

The mount `id` is `<cache-key>-<directory>`, and `--cache-key` is a **CLI flag the platform sets**. So
the app declares *directories* and the platform owns the *namespace* — the precise division of labour
this idea wants, already shipping. The overrides `-i/--install-cmd`, `-b/--build-cmd`, `-s/--start-cmd`,
`--pkgs`, `--apt` also come from the caller, not the repo.

### Railpack (Nixpacks' successor; Dokploy build type) — `railpack.json`

```json
{
  "$schema": "https://schema.railpack.com",
  "provider": "node",
  "buildAptPackages": ["git"],
  "packages": { "node": "22" },
  "caches": {
    "npm-cache": { "directory": "/root/.npm", "type": "shared" },
    "apt-cache": { "directory": "/var/cache/apt", "type": "locked" }
  },
  "steps": {
    "install": { "commands": ["npm install"], "caches": ["npm-cache"] }
  },
  "deploy": { "startCommand": "node dist/index.js" }
}
```

Caches are first-class and named at the top level, with `type: shared|locked` mapping straight onto
BuildKit's `sharing=`. This is the closest published schema to "a bash builder plus a set of folders to
cache" — worth reading before designing ours.

### Cloud Native Buildpacks / Paketo (Dokku's `builder-pack`) — `project.toml`

```toml
[_]
schema-version = "0.2"

[[build.env]]
name = "BP_JVM_VERSION"
value = "21"

[[build.env]]
name = "BP_MAVEN_BUILD_ARGUMENTS"
value = "-Dmaven.test.skip=true package"
```

Java knobs: `BP_JVM_VERSION` (defaults to 17.x), `BP_MAVEN_BUILD_ARGUMENTS` (default
`-Dmaven.test.skip=true package`), `BP_MAVEN_BUILT_ARTIFACT` (default `target/*.[jw]ar`),
`BP_GRADLE_BUILD_ARGUMENTS` (default `--no-daemon assemble`). No Dockerfile anywhere; there is no
`FROM` for the app to choose. Dependency reuse across builds is a **host volume the platform mounts** —
`pack build --volume $HOME/.m2:/home/cnb/.m2:rw` — so the cache path is again the caller's choice, and
per-app if the caller makes it per-app.

### Heroku buildpacks / herokuish (Dokku's default builder) — three small files

```
system.properties     java.runtime.version=21
Procfile              web: java -Dserver.port=$PORT -jar target/app.jar
app.json              { "scripts": { "dokku": { "predeploy": "…" } } }
.buildpacks           https://github.com/heroku/heroku-buildpack-java
```

Same division: the repo declares intent, the platform owns the image. Its cache handling — a per-app
docker volume `cache-$APP` mounted at `/cache` — is `enforce-cache-mounts.md`' subject.

### CapRover — `captain-definition` with the Dockerfile inline

```json
{
  "schemaVersion": 2,
  "dockerfileLines": [
    "FROM eclipse-temurin:25-jre",
    "COPY ./target/app.jar /app/app.jar",
    "CMD [\"java\", \"-jar\", \"/app/app.jar\"]"
  ]
}
```

Also `dockerfilePath`, `imageName` (prebuilt, no build) and `templateId` (`node`, `php`,
`python-django`, `ruby-rack`). Inline lines still live in the repo, so this is a *packaging* variant,
not platform ownership — but it proves the shape: a Dockerfile as data in a config file.

### Dokku — no build file at all, the box holds the config

```bash
dokku builder:set             APP selected dockerfile   # or herokuish | pack | lambda | null
dokku builder-dockerfile:set  APP dockerfile-path .dokku/Dockerfile
dokku docker-options:add      APP build '--cache-to type=local,dest=/var/cache/…/APP'
dokku git:from-image          APP shepherd/APP:latest   # with builder:set … null — no build at all
```

The interesting row for this idea: the build recipe *may* come from the platform side, and
`git:from-archive` / `git:from-image` accept a tree or an image that Shepherd assembled — so a generated
Dockerfile has a delivery channel that is not "commit it to somebody else's repo".

### And the shape this repo already has

`shepherd-build` is the counter-example: the repo's `Dockerfile` is the contract (`R_java_docker`), the
build command carries per-project `--cache-from`/`--cache-to type=local`, and the cache *mount* — the
one thing the build command cannot reach — is the app's business. Hence the gap.

## What it costs

- **Base-image policy becomes ours.** Once Shepherd writes `FROM`, every project needs a declared JDK
  and an escape hatch for native dependencies (apt packages, `git`, native libs). That is the slow slide
  into maintaining a buildpack — which is why adopting Paketo or herokuish outright deserves pricing
  against writing one. The whole survey above is products that took that road already.
- **It contradicts `R_java_docker` as worded** — "no language detection or buildpack magic is wanted;
  the `Dockerfile` is the contract". That requirement and `R_cache_isolation` now pull in opposite
  directions, and this idea resolves the tension by giving up the first. Deciding that *is* the decision.
- **Multi-module and non-JVM projects.** A single `command` + `artifact` glob covers a Vaadin-Boot fat
  jar; it does not obviously cover a repo whose Dockerfile does something bespoke (a frontend build
  stage, a native-image build, a non-JVM demo). Those need either an escape hatch back to a repo
  Dockerfile — which reopens the hole for exactly those projects — or `I_enforced_cache_mounts`.
- **A generated Dockerfile is not a sandbox.** The declared build command still runs the repo's own
  Maven/Gradle logic in the build container with that project's cache mounted, and build args stay
  visible to it. What is gained is that the *namespace* is Shepherd's, so pollution stays inside one
  project. Bounding what the build itself does remains the job of the build memory/CPU limits.

## Open questions

- Adopt an existing renderer (`nixpacks build --out`, or Paketo via `pack`) or template our own
  Dockerfile? Adopting means inheriting a build-plan schema and its language detection; templating means
  ~50 lines of Bash we fully control and no `FROM` we did not choose.
- Where does the spec live — a `shepherd.json` in the repo (still the app's file, but data rather than
  executable build steps) or the box-side per-project record (nothing to add to a foreign repo)? The
  second is the only one that works for repos we do not own, which is most of them (`D_poll_scm`).
- Does the generated file get committed anywhere, or rendered per build into a temp dir? Rendering
  per build means the operator has nothing to inspect after a failure; writing it next to the build log
  costs nothing.
- Is the cache-dir list per project, or a per-language default (`/root/.m2`, `/root/.gradle/caches`,
  `/root/.gradle/wrapper`) that a project may extend but not redirect?
